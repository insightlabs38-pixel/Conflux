# S22 — Advanced accessibility audit

## Result
Complete. An organizer composing the public event page can now see real,
computed WCAG-grounded warnings across the page's theme and blocks:
contrast, heading structure, accessible link names, and keyboard
operability.

## Changes
- `presentation.accessibility`: a pure `contrast_ratio` (WCAG relative
  luminance) plus `audit_theme`/`audit_page`. Rules check what a `Page`/
  `PageBlock` can actually contain today -- there are no images anywhere
  in the product's public content model, so "alt" maps to the real
  equivalent gap: vague/undescriptive link text (hero/CTA/resources/
  sponsors) per WCAG 2.4.4. Heading checks cover duplicate `<h1>` (two
  hero blocks) and rich-text heading-level skips; keyboard checks catch
  the one way the existing sanitizer can emit a non-focusable link
  (`<a>` with no `href` surviving `href=""`).
- New organizer-only `GET .../page/accessibility-audit/`, purely
  advisory -- never blocks saving or publishing.
- `PageBuilder` shows the warnings live, refreshed after every
  theme/block change.

## Verification
- Backend: `pytest` full suite 602 passed/8 skipped; new
  `tests/integration/test_accessibility_audit.py` (10 tests: contrast
  formula against the black/white reference, all three real themes
  clean, each of the four warning categories, permission).
- `ruff check`/`ruff format --check`, `makemigrations --check` (no model
  changes), `openapi`/SDK check: all clean.
- Frontend: `pnpm test` 78 passed (2 new), `tsc --noEmit`, `vite build`,
  `pnpm format:check`: clean except the pre-existing, out-of-scope
  `master/worker_prompt.md` finding.

## Limitations
- Theme colors are a hand-maintained constant mirroring
  `src/web/styles/tokens.css` (no shared build step exists between the
  Django backend and the Vite frontend for design tokens); a future
  palette change must update both.
