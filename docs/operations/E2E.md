# Browser journeys, screenshots and clips

`tests/e2e` holds Playwright specs that run against a live, demo-seeded stack (`scripts/demo-reset`, see [DEMO.md](DEMO.md)).

```sh
E2E_BASE_URL=http://localhost:8080 npx playwright test -c tests/e2e/playwright.config.ts
# demo media (screenshots + video; otherwise runs are failure-first): E2E_CAPTURE=visual ... scenes
```

Env: `E2E_BASE_URL`, `E2E_DEMO_SEED` (7), `E2E_DEMO_PASSWORD` (demo-pass-7). Chromium must be installed (`npx playwright install chromium`).

- `signin`, `public`, `roles`: sign-in/out, public pages, organizer/judge/participant workspaces at 1280×800 and 390×844 — no console errors or failed requests, no horizontal overflow, axe WCAG 2 A/AA clean, skip-link and focus-ring keyboard checks. Loading states must resolve before assertions.
- `scenes` (desktop): deterministic screenshots in `tests/e2e/artifacts/scenes/` and one video per scene under `artifacts/results/*/video.webm`, both only with `E2E_CAPTURE=visual`. Failures keep a screenshot and page snapshot; `scripts/e2e-tiers` adds a trace by re-running the failing files (`npx playwright show-trace`).
- `lifecycle` (desktop, serial; videos retained with `E2E_CAPTURE=visual`): the recorded demo lifecycle through the UI only — participant creates team and project, uploads a technical brief, submits and receives a signed receipt; organizer requests changes, participant remediates, organizer clears; three judges inspect artifacts and score; organizer publishes results, finalizes in the deliberation room, publishes the award; the public results page shows it. Needs a fresh `scripts/demo-reset submitted` (it consumes participant-24); if the demo was not reset the first step fails within 10 s with a message saying so.
- `pvs`: mentor desk, volunteer check-in by pass, participant RSVP/office hours/mentor request, deadline-exception request and decision, rules publish and acknowledge, and a layout/axe check of every organizer operations panel (also at 390×844). Workflows run on desktop only; run after a reset.
- Addressing: people by username, the event through the API; the event's public ID is also stable across resets.

- `extended-embed`: loads the built gallery Web Component against the live
  public API without cookies; included by `make verify-dogfood-extended`.
- Media handoff: `scripts/package-demo-media submitted` after a successful
  submitted run; repeat with `published` after its scene run, then use
  `scripts/package-demo-media --zip`. See [DEMO.md](DEMO.md).

- `pdv3-baseline-census` (opt-in, `E2E_CENSUS=1`, run after `scripts/demo-reset`): measurement-only tour that writes full-page JPEGs and a `manifest.json` (console/HTTP problems, horizontal overflow, axe counts) for every role at 1280×800 and 390×844 to `docs/verification/PD-B00/ui-census/`. It asserts nothing about layout and is skipped in normal runs.

## Isolated browser fixture contract (PD-B03-T01)

Normal mutable specs must not depend on the one long-lived `demo-hackathon-7` event. The contract below is what `PD-B03-T02…T11` implement; evidence is in `docs/verification/PD-B03/`.

**Canonical primitive.** A fixture is one generated demo scenario: `manage.py demo_scenario create --seed N …` then `manage.py demo_showcase demo-hackathon-N` (exactly what `scripts/demo-reset` runs). Built through the real API, so invariants/audit/permissions apply. No new model or seed path. Seed `N` fixes the workspace slug `demo-hackathon-N`, the workspace/event public IDs and every account (`demo-hackathon-N-<label>`); `support.ts` already selects it via `E2E_DEMO_SEED`/`E2E_DEMO_PASSWORD`.

**Fixture handle** (what a factory returns to specs and storage-state setup; one per worker/shard/test as the tier needs):

```ts
type Fixture = {
  seed: number;
  slug: string; // demo-hackathon-<seed>
  workspace: string;
  event: string; // public IDs (derived from seed)
  password: string; // per fixture; accounts share it
  profile: "iso-min" | "iso-judged" | "iso-published" | "canary";
  account(label: string): string; // demo-hackathon-<seed>-<label>
  dispose(): Promise<void>; // purge via demo_scenario purge <slug>
};
```

**Seeds.** `7` is the shared _reference_ (read-only tier; rebuilt only by `scripts/demo-reset`). `1…999999` belong to people/demos (e.g. 81–83) and are never touched. Factory seeds are `10_000_000 + nonce·1000 + slot` (`nonce` 0–9999 per run, `slot` 0–999 per fixture within the run; fits the `PositiveIntegerField`). A taken seed is refused by the generator (`already exists; purge it first`), so the factory picks a new nonce and never reuses or purges a seed it did not create; `dispose` and sweeps only act on seeds ≥ 10_000_000.

**Profiles** (sizes from labels the specs actually use: `participant-05`, `judge-03`; `participant-24` only in the lifecycle; `mentor/volunteer/sponsor` come from `demo_showcase`). Times are measured on the shared stack including ~1.3 s `docker compose exec` overhead.

| profile                    | size / checkpoint             | create + showcase | used by                         |
| -------------------------- | ----------------------------- | ----------------- | ------------------------------- |
| reference                  | 24p/6j submitted, seed 7      | `demo-reset`      | read-only tier                  |
| iso-min                    | 6p/3j, `--live 2`, submitted  | 3.4 s + 1.9 s     | isolated-mutation tier          |
| iso-judged / iso-published | 6p/3j, `--live 2` / `0`       | ≈3 s + 1.9 s      | specs needing ballots / results |
| canary                     | 24p/6j, `--live 2`, submitted | 8.3 s + showcase  | lifecycle chain (one per run)   |

Boundaries (all produce a diagnostic, none silently degrade): 3–40 participants, 2–12 judges; `--live` ≤ participants−2 (so 3p/2j needs `--live 1`); `published` requires `--live 0`; duplicate seed refused. Four concurrent creations of 4p/2j took 2.8 s wall (same as one), so factories may create per shard in parallel.

**Tiers** (specs run unmodified on an isolated seed; `pvs` 10/10 and event-themes/profiles/participant-workflow/uiv2-judge 26/26 passed on `iso-min`):

- _read-only on reference:_ `workspace-shell`, `roles`, `signin`, `extended-embed`, `uiv2-surfaces`, `uiv2-gate` (logout only), `public`, `showcase`, `foundations`. They move to isolated seeds only if a run needs the reference stable after a mutator.
- _isolated-mutation (iso-min, own seed):_ `event-themes` (PATCHes event brand), `profiles`, `participant-workflow`, `pvs`, `uiv2-judge`.
- _lifecycle canary (serial, `canary` profile, never parallelised or shortened):_ `lifecycle`. Consumes `participant-24`; still the authoritative create→submit→judge→publish→public-results path.
- _post-lifecycle readers:_ `uiv2-organizer`, `uiv2-final-states`, `scenes` read state the canary creates. `uiv2-organizer` fails on a generator-`published` seed (`404 …/awards/<id>/deliberation/`: the generator decides awards but never opens a deliberation), so these run on the canary's fixture after `lifecycle`, or T02 adds a canonical deliberation-finalize step; they must not be pointed at `iso-published` as-is.
- _opt-in measurement:_ `pdv3-baseline-census` (reference).

**Lifecycle.** create in worker/shard setup (before any test), sign-in via T03 storage states, dispose on success, **keep on failure** and print the slug so the failing state can be inspected; a sweep purges leftover seeds ≥ 10_000_000. Open checkpoints use the real clock for the submission window, so deadline-sensitive specs are per fixture.

**Guards.** A fixture's event ID must differ from the reference's; cross-fixture access must be denied (measured: organizer of one seed gets 403 reading/writing another's event) and a mutation on one fixture is invisible to another and to seed 7 (`docs/verification/PD-B03/probe_isolation.py`, 12/12).

**Implementation (T02).** `integrations/e2e_fixtures.py` + `manage.py e2e_fixture create <profile> | dispose <slug> | sweep | list` (one process: generator + showcase, JSON handle on stdout, random per-fixture password, taken seeds skipped, half-built fixtures purged on failure, `dispose`/`sweep` refuse anything below seed 10,000,000). Specs use `tests/e2e/fixtures.ts`: `isolatedTest("iso-min")` gives a worker-scoped `fixture` (created before the worker's first test, disposed after its last unless a test failed or `E2E_KEEP_FIXTURES=1`); `signIn(page, label, fixture)` signs in as its account. `E2E_MANAGE` overrides how `manage.py` is reached. `make e2e-fixture-sweep` purges fixtures older than `E2E_SWEEP_MINUTES` (30). The app container bakes the source, so run `docker compose up -d --build app` after pulling this command. Measured create: iso-min 4.1 s, iso-judged 4.3 s, iso-published 4.8 s, canary 9.0 s; four parallel iso-min 4.2 s wall (`docs/verification/PD-B03/logs/T02-create-timing.log`). `fixture-isolation.spec.ts` proves isolation, cross-fixture denial and scoped disposal.

**Storage states by role (T03).** `tests/e2e/auth-states.ts` signs in once per (scenario, role) through the API (`POST /accounts/login/`) and caches a Playwright storage state under `artifacts/e2e-auth/<seed>/<label>.json` (atomic write, safe across workers). Before each reuse it is revalidated against `/accounts/me/` (username match, cookie expiry with a 5-minute margin), so a revoked or expired session is re-issued transparently; a failed sign-in throws `storage state for <user>: sign-in failed (HTTP n); is the scenario seeded … correct?` and writes nothing. Specs get `as(label)` (page signed in as that role in the test's own context) and `as.other(label)` (separate context, for two identities at once) from `referenceTest` (seed 7) or `isolatedTest(profile)` (the fixture's accounts). **Opt-out:** sign-in, sign-out and authorization specs keep using `signIn()`/the real form, and any spec that signs out must not use a state, because logout revokes the server-side session behind it (proved in `auth-states.spec.ts`). `roles.spec.ts` is the first adopter: 10 tests 15.6 s → 12.7 s (mean of two runs each, desktop+mobile; `docs/verification/PD-B03/logs/T03-roles-*.log`).

**Tiers in practice (T04).** `tests/e2e/tiers.json` is the single classification (`scripts/e2e-tiers check`, part of `make lint`, fails for any unclassified or duplicated spec). `make e2e-fast` → `scripts/e2e-tiers` runs the tiers concurrently: _read-only_ + _self-isolating_ specs in one 4-worker run on the demo event; _isolated-mutation_ specs one `iso-min` fixture **per file** (`E2E_ISOLATED_JOBS`, default 3 concurrent); the _canary_ chain `lifecycle → scenes → uiv2-organizer → uiv2-final-states` serially on its own `canary` fixture. Specs are unmodified (identity arrives as `E2E_DEMO_SEED`/`E2E_DEMO_PASSWORD`), so no `scripts/demo-reset` is needed between runs and seed 7 is never mutated by the fast path. Run one tier with `scripts/e2e-tiers run <tier>`. Fixtures are disposed on success and kept on failure (slug printed; `make e2e-fixture-sweep`). `make demo-e2e` is still the serial, reset-first authority against seed 7. Measured on the baseline suite: 3m48s → 2m49s / 2m47s (two runs), 152 passed / 99 skipped, 0 failed — the 144 baseline passes plus the 8 new fixture/state specs (`docs/verification/PD-B03/logs/T04-tiers-full-run*.log`). The read-only run (2.6 min, 4 workers) is now the critical path.

**Persistent stack (T05).** Browser runs reuse the one running compose stack; nothing is rebuilt or reset unless the suite's semantics need it. `scripts/e2e-stack status` (`make e2e-stack`) checks health, that the reference scenario signs in and its event window has ≥ 12 h left (the `submitted` checkpoint uses a real-clock window), that the running API matches `src/api` **by content** (web bundle by mtime; skipped under the `make dev` bind-mount overlay), leftover fixtures and Chromium. `ensure --fix` (`make e2e-stack FIX=--fix`, run automatically by `scripts/e2e-tiers`; skip with `E2E_SKIP_PREFLIGHT=1`) repairs only what is wrong: a stopped stack gets `docker compose up -d` (no build), a missing/expired reference gets `scripts/demo-reset submitted`; a healthy stack costs ~1.8 s versus ~14 s for a reset. Stale images only warn (`--require-fresh` makes them fail) because the fix is a deliberate `make up`. Use `make dev` for Vite/Django hot reload and point `E2E_BASE_URL` at it. Evidence: `docs/verification/PD-B03/logs/T05-*.log`.

**Smoke and affected selection (T06).** Four tiers of feedback, widest last: `make e2e-smoke` (sign-in, role workspaces, public pages; desktop only; 16 tests in 8.3 s, 10.9 s with preflight) → `make e2e-affected` (only specs mapped from changed paths, vs `BASE`, default uncommitted + untracked; `LIST=1` prints the selection and why) → `make e2e-fast` (PR: all tiers, ~2m48s) → release: `make demo-e2e` serial against a reset seed 7 plus the canary. The mapping is `tests/e2e/affected.json` (paths use `fnmatch`, `*` spans `/`): shared shell/components/styles, e2e infrastructure, Makefile and workflows select **everything**; docs and unit tests select nothing; a mapped feature or API app selects its specs; an unmapped `src/`/`scripts/` path falls back to smoke with a visible "add a rule" reason, never silently to nothing; a changed spec selects itself. Selecting any canary member runs the chain up to it (`lifecycle → scenes → uiv2-organizer → uiv2-final-states`) on a fresh `canary` fixture. `tests/test_e2e_tiers.py` pins the mapping and fails when a spec or rule is unclassified. Evidence: `docs/verification/PD-B03/logs/T06-smoke-affected.log`.

**Failure-first capture (T07).** Routine runs record nothing: no video, no trace, no explicit screenshots; Playwright keeps a screenshot and page snapshot (`error-context.md`) of failing tests. Explicit specs screenshots go through `capture()` (`support.ts`) and video through `E2E_CAPTURE`, so **visual campaigns** are opt-in: `E2E_CAPTURE=visual` (set by `make demo-e2e`; use it for design review and demo media). Traces cost ~20% of a read-only run just to be discarded on success (121–125 s → 96 s with them off), so `scripts/e2e-tiers` re-runs the failing spec files of the read-only and isolated tiers once with `E2E_TRACE=on` into `artifacts/e2e-fast/<group>-diagnose/` and prints the path; the tier stays failed whatever the re-run does, and a re-run that passes is reported as flaky/state-dependent, never as a pass. The canary chain consumes its state, so it is not re-run: its fixture is kept instead. Switch one knob on for a local debug run with `E2E_TRACE=on|retain-on-failure`, `E2E_VIDEO=on|retain-on-failure`; `E2E_NO_DIAGNOSE=1` skips the re-run. Full `make e2e-fast` with failure-first capture: 138.5 / 137.8 / 138.1 s, 152 passed, 0 failed (was 2m47–2m49 with traces on). Measurements: `docs/verification/PD-B03/logs/T07-*.log`.

Two test races surfaced by the faster, more concurrent runs were fixed at the root rather than retried: `uiv2-gate` pressed Tab before the SPA had mounted (21/240 failures under 8 workers → 0/240, `T07-gate-race-fix.log`), and `lifecycle` matched "Finalist comparison" by text, which is ambiguous once the finalize form has rendered (strict-mode violation) — it now addresses the table region.

**Sharding (T08).** `scripts/e2e-tiers run --shard I/N` (`make e2e-fast SHARD=I/N`) runs one slice of the PR suite; `scripts/e2e-tiers plan N` prints the split and its balance. The unit of work is a spec file (read-only, self-isolating and isolated-mutation) or the whole canary chain, which is never split. Units are assigned by a deterministic longest-processing-time split over `tests/e2e/weights.json` (serial-equivalent seconds; refresh with `scripts/e2e-tiers weights` after a full run; `tests/test_e2e_tiers.py` fails if a unit has no weight). Plans: 2 shards ~191 s each, 3 shards ~128 s, 4 shards ~121 s (the canary chain alone is the floor). **Collision safety**, by design and proved by running `--shard 1/2` and `--shard 2/2` **concurrently on the one shared stack** (92 + 60 = 152 passed, 51 + 48 = 99 skipped, 0 failed — identical to the unsharded totals; `docs/verification/PD-B03/logs/T08-shard-*.log`): identities come from per-fixture random seeds (distinct per shard), outputs and logs go to `artifacts/e2e-fast/s<I>of<N>-<group>/`, storage states are atomic and revalidated, read-only specs never mutate the reference, and stack repair (`e2e-stack ensure --fix`) takes a file lock so two shards cannot both start the stack or reset the reference. Ports only matter when each shard brings its own stack on one host: set a distinct `COMPOSE_PROJECT_NAME` and `CONFLUX_PORT` and point `E2E_BASE_URL` at it. One machine gains nothing from sharding (the shards contended: 2m23s for both); the benefit is across CI jobs. **CI recipe** (not yet added to `.github/workflows/ci.yml` because it cannot be exercised here): per matrix job `shard: [1, 2, 3, 4]`: check out, `docker compose up -d --build`, `npx playwright install --with-deps chromium`, `scripts/demo-reset`, `make e2e-fast SHARD=${{ matrix.shard }}/4`, upload `artifacts/e2e-fast/**` on failure.

**Lifecycle canary as the release/nightly gate (T09).** Isolation must not hide integration failure, so the real create → submit → remediate → judge → publish → award path stays whole and authoritative: the canary chain (`lifecycle → scenes → uiv2-organizer → uiv2-final-states → release-integrity`) always runs as one serial unit on its own fresh `canary` fixture, is never split by sharding and never sampled by `e2e-affected` (any change under the judging, awards, projects or participation paths selects it). `release-integrity.spec.ts` closes the chain with API-level checks of what the UI journey left behind: all applications approved; 3 distinct judges' ballots in the provenance snapshot and a converged normalization run; results contain exactly the scored project; the signed `EdDSA` submission receipt names the published project; the award is published with a deliberation room, visible to an anonymous client; the audit log holds submit → ballot → normalization → results → deliberation → award in causal order with the right actors; and participants/anonymous clients are still denied the organizer and audit endpoints. It detects breakage: on a fixture where the lifecycle did not run it fails (`submitted_ballots` 0 ≠ 3), and after deleting one ballot behind the API it fails (2 ≠ 3) (`docs/verification/PD-B03/logs/T09-integrity-gate-detects-breakage.log`). Gates: `make e2e-canary [REPEAT=N]` (N fresh fixtures, all must pass, pass rate printed; nightly use `REPEAT=3`; failed runs keep their fixture) and `make e2e-release` (`demo-reset` + the serial `make demo-e2e` with visual capture + the canary gate). The serial `make demo-e2e` only orders correctly because no spec overrides fixture options: Playwright runs specs with different `test.use` options as separate worker groups, which had silently pushed `lifecycle` _after_ `uiv2-organizer` (5 failures in the first `make e2e-release`); video now comes from the config and `E2E_CAPTURE`, so one alphabetical group keeps `lifecycle` before `release-integrity`, `uiv2-final-states` and `uiv2-organizer`. Serial run after the fix: 156 passed, 133 skipped, 0 failed, 9.0 min (`T09-serial-demo-e2e.log`). A scheduled GitHub workflow running `make e2e-canary REPEAT=3` nightly and `make e2e-release` before a release is the intended wiring; it is not added to `ci.yml` because it cannot be exercised here.

**Timing and reliability targets (T10).** Every `scripts/e2e-tiers` invocation appends one line (kind, wall, passed/skipped/failed/flaky, slowest specs, diagnostic re-runs, commit) to `artifacts/e2e-fast/history.jsonl`; `make e2e-report` (`scripts/e2e-tiers report [--check] [--kind K] [--window N]`) compares the last N runs with `tests/e2e/targets.json` and lists flaky events (a spec that failed and then passed on its diagnostic re-run). Targets leave about 50% headroom over what was measured on this single 8-core host, so they flag real growth rather than noise; tighten them only with new measurements.

| Tier                | Command                    | Target (wall)                           | Measured                                                     | Notes                                                                                   |
| ------------------- | -------------------------- | --------------------------------------- | ------------------------------------------------------------ | --------------------------------------------------------------------------------------- |
| Smoke               | `make e2e-smoke`           | ≤ 20 s                                  | 11 s (3 runs), 16 tests                                      | sign-in, roles, public pages, desktop only                                              |
| Affected            | `make e2e-affected`        | ≤ 120 s                                 | 35–49 s for one mapped isolated spec (pvs)                   | scales with selection; shared-infrastructure changes select ALL and count as a full run |
| PR / full           | `make e2e-fast`            | ≤ 210 s median                          | 141 s median, 142 s max over 10 consecutive runs, 152 passed | was 3m48s before PD-B03; read-only tier is the long pole                                |
| PR sharded (4 jobs) | `make e2e-fast SHARD=i/4`  | design floor ≈ 120 s (the canary chain) | not measured across machines                                 | one host gains nothing; see Sharding                                                    |
| Canary gate         | `make e2e-canary`          | ≤ 150 s per run                         | 115–120 s per fresh-fixture chain                            | release/nightly: `REPEAT=3`                                                             |
| Release serial      | `make demo-reset demo-e2e` | ≤ 12 min                                | 9.0 min, 156 passed                                          | authoritative, visual capture on                                                        |

**Reliability budget:** in any window of 10 consecutive runs of a kind, 0 failures and 0 flaky events (`report --check` fails otherwise, and also when the median exceeds its target or the latest full/canary run is red). Current evidence: 10/10 consecutive full runs green with 0 flaky events (`docs/verification/PD-B03/logs/T10-history.jsonl`, `T10-report-all.log`), plus three earlier full runs after the capture change. A diagnostic re-run that passes is never a pass: it is reported as a flaky event and fails the budget. Flake triage order: read the failing group's `tier-<group>.log`, open the `-diagnose` trace, re-run the spec with `--repeat-each` under `--workers=8` to reproduce load-dependent races (this is how the `uiv2-gate` and `lifecycle` races were found), fix the test or the product at the root; never raise a timeout or add a retry.

**Known limits.** Creation scales roughly with account count (8.3 s for 31 accounts, ≈0.25 s each including the API replay), so keep mutation-tier fixtures small. Factory, storage states, tier split and sharding are later tasks (T02–T08).
