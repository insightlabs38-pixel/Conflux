# VS25 — Permission matrix explorer

## Result
An organizer can see, for every registered API endpoint, exactly which
workspace roles (or "any signed-in user"/"public") the real permission
check allows -- computed by introspecting the actual DRF
`get_permissions()` machinery, not a separately maintained description
of it, so the matrix can never silently drift from what's enforced.

## Changes
- `core.permission_matrix.build_permission_matrix()`: walks the live
  Django URL resolver tree, and for every (registered `APIView`, HTTP
  method) pair, instantiates the view with a minimal fake request
  (`.method` only -- confirmed sufficient, since every `get_permissions()`
  override in this codebase branches on that alone) and calls the real
  `get_permissions()`, then classifies each returned permission instance
  as role-scoped (`HasWorkspaceRole`/`require_roles`), any-workspace-member
  (`IsWorkspaceMember`), any-authenticated-user, or public
  (`AllowAny`) -- 282 real endpoint/method pairs found, all recognized.
- New organizer-only `GET .../permission-matrix/` returns the full list
  (`resource`/`view`/`path`/`method`/`access`/`roles`).
- `PermissionMatrixExplorer.tsx` on `EventDashboard`: a role dropdown
  filters the fetched matrix client-side to "what can this role (plus any
  endpoint open to any signed-in user or the public) reach."

## Limitations
- Recognizes exactly the four permission-class shapes this codebase
  actually uses (`HasWorkspaceRole`/`require_roles`, `IsWorkspaceMember`,
  `IsAuthenticated`, `AllowAny`); a future view using something else would
  surface honestly as `"access": "unknown", "unrecognized": true` rather
  than silently misreporting it, but it wouldn't be resolved automatically.
- The matrix is workspace/event-independent (permission classes don't
  vary by event); the event in the URL is only where the tool lives in
  the organizer dashboard, not a scoping filter on the data itself.
- Object-level checks inside view bodies (e.g. "only the ballot's own
  judge may read it") aren't visible here -- this reports the
  `permission_classes`/`get_permissions()` gate only, the first of
  potentially several authorization layers a request passes through.
