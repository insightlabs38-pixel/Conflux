# VS02 — Adaptive pairwise scheduling

## Result
Complete. The pairwise "next comparison" scheduler now prefers the pair
whose current Bradley-Terry strength estimates are closest (the most
informative, least-predictable comparison to run) once any PairwiseRun
exists, while a bounded fairness window keeps coverage from drifting;
before any run exists it degrades to the original coverage-only choice.

## Changes
- `evaluations.pairwise.select_next_pair`: two-stage, deterministic
  (ties always broken by ascending-id traversal order). Stage 1 restricts
  to candidates within `FAIRNESS_SLACK` (1) comparisons of the field's
  current minimum. Stage 2 picks, among not-yet-judged-by-this-judge
  pairs in that pool, the one with the smallest
  `|strength_a - strength_b| / (strength_a + strength_b)` -- or, with no
  `strengths` yet, the original minimal-total-load choice. Falls back to
  the unrestricted candidate set only if the fair pool alone has nothing
  left to offer.
- `PairwiseNextPairView` now fetches the plan's latest `PairwiseRun` and
  delegates to `select_next_pair` instead of its old inline minimal-load
  loop; response shape and permissions are unchanged.
- `assignment.py`'s `_track_fit`/`_build_evidence` naming from VS01 is
  unrelated and untouched here; this batch only touches `pairwise.py`.

## Verification
- Backend: `pytest` full suite 633 passed/8 skipped; new
  `tests/integration/test_adaptive_pairwise_scheduling.py` (8 tests: pure
  `select_next_pair` unit tests for the no-run fallback, strength
  preference beating a lower-load alternative, fairness-slack exclusion,
  already-judged exclusion, degenerate inputs; an end-to-end API test
  proving the live endpoint picks the run-informed pair over the
  pure-coverage pick a second judge's redundant comparison would
  otherwise produce; a no-run-yet fallback test).
- `ruff check`/`ruff format --check`, `makemigrations --check` (no model
  changes): clean. `openapi.yaml` regenerated (the view's docstring,
  which spectacular includes as the endpoint description, changed);
  `generate_sdks.py --check` stayed clean (no generated-code change).
- No frontend UI exists for pairwise comparisons at all (judge or
  organizer) -- the same API/SDK-only boundary S01's own assignment
  preview/activate/rebalance endpoints already have -- so none was added.

## Limitations
- `FAIRNESS_SLACK` is a fixed constant (1), not organizer-configurable;
  no post-spec requirement asked for that knob.
