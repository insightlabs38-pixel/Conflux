# VS01 — Optimization-grade assignment solver

## Result
Complete. A new explicit min-cost-flow solver optimizes judge/project
assignment (hard conflicts, coverage, convex load balancing, track-fit)
for the assigned-subset strategy, additive to and comparable against the
existing greedy heuristic.

## Changes
- `evaluations.optimization.MinCostFlow`: a from-scratch, dependency-free
  successive-shortest-augmenting-path min-cost flow solver (SPFA per
  augmentation; every edge cost here is non-negative by construction).
  `compute_assignment_optimized`: models source->judge->project->sink,
  with a hard conflict enforced structurally (no edge exists), coverage
  as flow capacity, load balanced via convex per-judge marginal cost
  (parallel unit-capacity edges with costs 0,1,2,...), and track-fit as a
  soft edge cost. Shares `assignment.repair_connectivity` afterward so
  both solvers are judged on connectivity identically.
- `assignment.py`: `_track_fit`/`_build_evidence` promoted to
  `track_fit`/`build_evidence` (no behavior change) since both solvers
  now share them; `build_evidence` gained a `solver` field.
- New organizer-only `POST .../assignments/compare/` (read-only,
  heuristic vs. optimized evidence side by side) and
  `POST .../assignments/activate-optimized/` (freezes a real
  AssignmentVersion from the optimized solver, same model/immutability/
  audit trail as the existing activate endpoint).

## Verification
- Backend: `pytest` full suite 625 passed/8 skipped; new
  `tests/integration/test_assignment_optimization.py` (11 tests: solver
  correctness on hand-worked track-fit and load-balance cases, no
  conflict/coverage violation, determinism, ALL_JUDGES rejection,
  end-to-end activation enforced on ballot submission, permissions).
- `ruff check`/`ruff format --check`, `makemigrations --check` (no model
  changes -- evidence stays a JSONField), `openapi`/SDK check: all clean.
- No frontend UI was added: the existing heuristic's own preview/
  activate/rebalance endpoints have never had one either (API/SDK-only),
  so this keeps the same, apparently deliberate boundary rather than
  introducing lopsided coverage.

## Limitations
- Connectivity stays a post-processing repair pass for both solvers, not
  a flow objective -- it isn't linear/convex in the same sense the other
  three dimensions are, so folding it into the LP would need a different
  (and materially heavier) formulation than this batch's scope justifies.
