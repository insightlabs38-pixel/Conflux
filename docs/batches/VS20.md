# VS20 — Appeal/dispute workflow

## Result
A project member can file a structured appeal once a plan's results are
actually published and visible to participants; an organizer records a
one-time verdict, fully audited, without ever mutating the frozen
ballot/normalization data underneath.

## Changes
- `evaluations.Appeal` (plan/project/submitted_by/body/status/
  decision_note/decided_by/decided_at). Deciding an appeal
  (upheld/overturned/dismissed) is a recorded verdict only -- any actual
  remedy still goes through the existing immutable paths (a new rubric
  edit, a fresh `NormalizationRun`, `tie_breaks`), matching how
  `AssignmentVersion`/`NormalizationRun`/`RubricVersion` are treated
  everywhere else in this app.
- `POST .../evaluation-plans/<id>/appeals/`: gated on the exact same
  `published_normalization_run` + `results_visible_to_participants` check
  `ResultsView` already enforces; the actor must hold PARTICIPANT and be
  a `ProjectMembership` of the named project.
- `GET .../appeals/`: organizer/admin see every appeal for the plan; a
  participant sees only their own.
- `POST .../appeals/<id>/decide/`: organizer/admin only, row-locked,
  rejects re-deciding an already-decided appeal.

## Limitations
- API/SDK-only: there is no participant-facing "my results" page in the
  frontend at all yet to attach an appeal button to (only organizer-side
  `EvaluationBuilder.tsx` exists) -- building that page is a materially
  larger, separate UI concern than this batch's workflow/audit goal.
- No automatic notification to the organizer when an appeal is filed;
  they discover it via the list endpoint.
