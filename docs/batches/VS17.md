# VS17 — Registration/application/waitlist presets

## Result
Complete. Events gain a first-class self-serve registration front door
(open/application/invite-only), with capacity, waitlist, and organizer
review, layered on the existing workspace `Membership` grant.

## Changes
- New `events` models: `EventRegistrationSettings` (mode/capacity/
  waitlist), `RegistrationInviteCode` (same validity/replay shape as
  `participation.TeamInvite`), `EventApplication` (per-event, one row per
  user, unique constraint).
- `events.registration`: `apply_to_event` (open auto-approves; invite-only
  redeems a row-locked code; application mode queues for review; capacity/
  waitlist decide automatically for the self-serve modes) and
  `decide_application` (organizer approve/waitlist/reject, row-locked,
  rejects re-deciding an already-decided application). Capacity is counted
  against this event's own `EventApplication` rows, not workspace
  `Membership` -- see the model docstring for why (a workspace can host
  several events).
- New endpoints: registration settings (GET/PUT), invite codes (list/
  create/revoke), applications (list/decide), and `my-application/`
  (GET/POST) -- the one endpoint any authenticated user can call without
  already holding a workspace membership, since granting one is its job.
- `RegistrationPanel.tsx`: organizer UI for settings, invite codes, and
  deciding pending/waitlisted applications, added to `EventDashboard`.

- `ruff format/check`, `makemigrations --check` (new

  `manage.py check`, OpenAPI/SDK check: all clean.

  files are clean.

## Limitations
- No public "apply" page/route exists yet -- the API is complete and
  ready for one, but building a new unauthenticated-to-authenticated
  entry route/page shell is a separate, materially larger UI concern than
  this batch's organizer-facing surface.
- No automatic waitlist promotion when an approved participant withdraws;
  an organizer decides each waitlisted application manually.
