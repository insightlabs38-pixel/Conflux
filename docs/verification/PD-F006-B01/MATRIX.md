## Cross-cutting checks

- Authorization and visibility: the one server change is the optional `search` parameter, which runs inside the entity's own `base(event, user)` rows and roles; a judge is refused before any search; the new tests cover it. Selection, bulk bar and paging only start existing, authorized workflows.
- Migration and compatibility: no model or migration. `search` is stored in a view definition only when used, so views saved before it read as before (the pre-existing stored-keys assertion passes untouched); OpenAPI and both SDKs were regenerated and `make verify-fast` checks them. Existing `sort_`, `page_`, `row_`, `view_` params keep their meaning; `size_` is new and ignored by older links.
- States and viewports: every spec runs at desktop and the 390 mobile project or says why it does not; loading, empty, error, refused-filter, offline (B03) and past-the-end states are in unit or browser tests; axe runs on each surface.
- Regressions found and fixed during this batch: the grid treated the whole sort parameter as one key (a second key would have been dropped); a selection survived a page change; every keystroke in a filter asked the server and showed an error page for a half-typed date; empty values ordered differently on PostgreSQL and SQLite; two web tests were flaky (a header read with or without its sort hint, headers not yet rendered) and now wait.
- CLI and MCP: the read path is T91's deliverable per the contract and is verified there.
