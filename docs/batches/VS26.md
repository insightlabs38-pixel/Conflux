# VS26 — Authorization policy test console

## Result
An organizer can dry-run whether a given endpoint/method would allow a
real user (their actual current workspace roles) or a bare hypothetical
role (no membership needed) -- without ever calling the endpoint's real
handler, extending VS25's static matrix into a live, queryable console.

## Changes
- `core.permission_matrix.dry_run(path, method, workspace, subject_kind,
  subject)`: `subject_kind="user"` instantiates the real view, builds a
  minimal fake request carrying the real `User` and `.method`, and calls
  the actual `get_permissions()`/`has_permission()` -- genuinely live,
  labeled `"mode": "live"`, and reports the user's real current roles for
  transparency. `subject_kind="role"` never fabricates a Membership row;
  it reclassifies the same static matrix VS25 built, labeled
  `"mode": "hypothetical"` so the two are never confused.
- New organizer-only `POST .../authz-dry-run/` wraps it, validating the
  role/path against real values before evaluating.
- `PermissionMatrixExplorer.tsx` gains a console: pick an endpoint from
  the matrix, pick "hypothetical role" or "real user (by ID)", and see
  Allowed/Denied plus the mode and (for a real user) their actual roles.

## Verification
- Backend: `pytest` full suite 733 passed/8 skipped; new

  matrix exactly, a live check against two real users with different
  actual roles gives the correct opposite answers, and the endpoint's
  organizer-only boundary plus input validation for an unknown role and
  a nonexistent path).
- Frontend: `vitest run` 95 passed (new dry-run interaction test:

- `ruff format/check`, `makemigrations --check` (none needed -- no model

- Repo-wide `pnpm format:check` still only fails on the pre-existing,

  campaign, unrelated and left untouched.

## Limitations
- "Live" mode only exercises the `get_permissions()`/`has_permission()`
  gate, never the view's actual handler body -- object-level checks
  inside a handler (e.g. "only the ballot's own judge may read it") are
  still invisible here, same boundary VS25 already documented.
- A hypothetical hypothetical-role result assumes the subject holds
  *only* that one role in the workspace; it can't model "a user who holds
  both PARTICIPANT and JUDGE," which only the live/real-user path can
  show.
