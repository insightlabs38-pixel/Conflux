# VS23 — Internationalization/localization

## Result
The public event site's own template chrome (nav, section headings,
placeholder/status messages) is translatable via real gettext catalogs;
Spanish is the first fully-translated locale. Organizer-authored content
(project names, page-builder block text) stays untranslated by design --
it's user data, not app UI.

## Changes
- `LocaleMiddleware` + `LANGUAGES = [en, es]` + `LOCALE_PATHS`; the
  `request` context processor (needed for the language-switcher form's
  "return to this page" hidden field) is the only addition to the
  previously-empty `TEMPLATES` context processor list.
- `{% trans %}`/`{% blocktrans %}` wrap the static strings in
  `base.html`/`event_landing.html`/`gallery.html`/`project_detail.html`;
  `<html lang="...">` reflects the active locale.
- A language-switcher form posts to Django's built-in `set_language` view
  (`/e/i18n/setlang/`), which sets the `django_language` cookie
  `LocaleMiddleware` reads on later requests -- no new session/cookie
  machinery of our own.
- `src/api/locale/es/LC_MESSAGES/django.po` (33 real Spanish
  translations, hand-written then verified byte-identical to a fresh
  `manage.py makemessages -l es` extraction) + its compiled `.mo`.
  `{{ event.starts_at }}`-style date/number output localizes to the
  active locale automatically (Django's default template behavior once
  `USE_I18N` is on) -- no extra work needed for that half of "locale-aware
  event display".
- `make messages`/`make compile-messages`/`make i18n-check` Makefile
  targets (real `manage.py makemessages`/`compilemessages`, i.e. real
  `xgettext`/`msgfmt`).

## Verification
- Backend: `pytest` full suite 722 passed/8 skipped; new `test_i18n.py`
  (3 tests: English default, `Accept-Language: es` rendering real Spanish
  text and `lang="es"`, and the `set_language` cookie persisting the
  choice across a second request).
- `ruff format/check`, `makemigrations --check` (none needed -- no model
  changes), `manage.py check`, OpenAPI/SDK check (the schema's own `lang`
  query param enum now correctly lists `en`/`es` instead of Django's ~100
  default languages, since `LANGUAGES` is now explicitly scoped): all
  clean. `make i18n-check` passes against the real `msgfmt`-compiled
  `.mo`.
- Repo-wide `pnpm format:check` still only fails on the pre-existing,
  untracked `master/` scaffolding from the abandoned orchestration
  campaign, unrelated and left untouched.

## Note on tooling
This environment initially had no `msgfmt`/`xgettext` (only `gettext-base`,
missing the full `gettext` package), so the first pass shipped a
hand-rolled, dependency-free `.po`-to-`.mo` compiler
(`scripts/compile_messages.py`) to unblock the batch. Per the owner's
explicit direction mid-batch, since a bespoke compiler misses plural
forms/`msgctxt`/fuzzy-filtering/validation and doesn't solve extraction at
all, `apt-get install gettext` was run (safe, additive, standard dev
dependency) and the batch now uses the real `manage.py
makemessages`/`compilemessages` end to end; the custom script was deleted
after confirming a real `xgettext` extraction matched the hand-written
catalog byte-for-byte in content.

## Limitations
- Only the public site's template chrome is translated -- the
  organizer/judge/participant React SPA has no i18n framework wired in at
  all; that would be a much larger, separate undertaking.
- One additional locale (Spanish) as a proof of the mechanism, not
  exhaustive language coverage.
- ARIA `aria-label` attributes on landmark `<section>`s stay in English
  (only visible heading text and body copy are translated); a follow-up
  could extend `{% trans %}` to those too.
