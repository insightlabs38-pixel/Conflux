# VS18 — Mentor/volunteer/sponsor roles

## Result
Three new workspace roles (MENTOR, VOLUNTEER, SPONSOR), each wired to
exactly one narrow capability; every existing authorization boundary is
mathematically unchanged since every view already gates on an explicit
role tuple.

## Changes
- `workspaces.Role` gains `MENTOR`/`VOLUNTEER`/`SPONSOR` -- inert until a
  view lists one by name (`require_roles(...)`), same mechanism every
  other role already uses.
- Mentor: `MentorNote` (project-scoped, private note), visible/writable
  only to mentor/organizer/admin -- never the project's own participants,
  never scoring (`projects.roles_views.MentorNoteListView`).
- Volunteer: `ParticipantCheckIn` (event-scoped attendance log, unique per
  participant), list/create gated to volunteer/organizer/admin
  (`events.checkin_views.CheckInListView`); rejects checking in a user who
  doesn't hold PARTICIPANT.
- Sponsor: read-only `sponsor-projects/` roster (name/team/track, no
  scores or private data) gated to sponsor/organizer/admin.

## Verification
- Backend: `pytest` full suite 710 passed/8 skipped; new
  `test_role_capabilities.py` (4 tests: mentor note isolation, volunteer
  check-in incl. duplicate/non-participant rejection, sponsor read-only
  roster, and an explicit boundary regression proving mentor/volunteer/
  sponsor gain zero access to an organizer-only and a membership-granting
  endpoint).
- `ruff format/check`, `makemigrations --check` (3 new migrations:
  `workspaces.0002_alter_membership_role`,
  `events.0003_participantcheckin`, `projects.0004_mentornote`),
  `manage.py check`, OpenAPI/SDK check, SDK `tsc` build: all clean.
- Repo-wide `pnpm format:check` still only fails on the pre-existing,
  untracked `master/` scaffolding from the abandoned orchestration
  campaign, unrelated and left untouched.

## Limitations
- API/SDK-only: no dedicated mentor/volunteer/sponsor frontend surface
  exists yet to log into (there is no self-serve UI for holding these
  roles at all), so building three new role-specific dashboards is out of
  scope for this batch's authorization-focused goal.
- No workflow yet grants these roles to a user (no invite/apply path);
  today an organizer sets them the same manual way as any other role via
  `WorkspaceMembersView`.
