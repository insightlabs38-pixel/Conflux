# VS15 — Historical assignment suggestions

## Result
Complete. A read-only endpoint ranks workspace judges not yet in a pool by
track-expertise match plus their prior workload/reliability elsewhere in the
workspace, so an organizer can decide whom to invite before assignment runs.

## Changes
- `evaluations.judge_suggestions.PoolJudgeSuggestionsView`:
  `GET .../evaluation-pools/<pool>/suggest-judges/` (organizer-only).
  Excludes existing pool members; ranks candidates by matched track tags,
  then completed ballots, then username, all deterministic.
- Evidence per candidate: expertise tags, matched tags, distinct past events
  with completed ballots, ballots completed, assignments received (from
  each historical plan's *active* version only, to avoid double-counting
  across rebalances), and a derived completion rate.
- Reuses VS14's `expertise.normalize_tag` and VS13's judge-directory role
  scoping; writes nothing (no invitation/membership/assignment mutation).
- Also fixed a pre-existing GCON-001/002 gate violation found by the full
  suite in `judge_directory.py` (two `select_for_update()` calls chained
  with `select_related()` missing `of=("self",)`), unrelated to this
  feature's own code but blocking a clean full-suite baseline.

## Verification
- New `tests/integration/test_judge_suggestions.py` (2 tests: ranking/
  evidence correctness and exclusion, organizer-only permission).
- Full backend suite: 700 passed/8 skipped (previously 1 failing on the
  select_for_update gate before the judge_directory.py fix, now clean).
- `ruff format --check`/`ruff check`, `makemigrations --check` (no model
  changes), OpenAPI/SDK check, `manage.py check`, SDK `tsc` build: all clean.
- No frontend UI added, matching VS04's API/SDK-only boundary for read-only
  explorers.

## Limitations
- Track matching is exact normalized-name matching (same as VS14); no
  fuzzy/synonym matching.
- Ranking is a fixed deterministic tuple (match count, then completed
  ballots, then username), not a tunable weighted score.
