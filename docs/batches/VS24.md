# VS24 — Advanced timezone/DST safeguards

## Result
Every `TemporalGate` (and the event's own start/end window) now carries
its event-local rendering and a DST-crossing warning alongside its
canonical UTC instant; the frontend shows per-viewer local time plus the
event's own local time, and a new organizer timeline lists everything
time-boxed about the event, sorted, in one place.

## Changes
- `policies.timezone_safety`: `local_iso` (an instant rendered in a given
  IANA zone) and `dst_warning` (non-null when a window's UTC offset in
  that zone differs between its open and close, detected by comparing
  `utcoffset()` at each endpoint -- correct regardless of window length,
  since offsets only change at real zone transitions).
- `TemporalGateSerializer` gains read-only `event_local_opens_at`/
  `event_local_closes_at`/`dst_warning`; `opens_at`/`closes_at` stay the
  writable canonical UTC fields, unchanged.
- New organizer-only `GET .../timezone-timeline/`: the event's own window
  plus every gate, sorted by UTC `opens_at`, each with the same
  local/warning annotations -- the "UTC canonical timeline" the goal asks
  for, built from the same helpers as the per-gate fields so there's one
  source of DST logic, not two.
- `PolicyBuilder.tsx`: gate creation gains `datetime-local` inputs
  (interpreted as the organizer's own browser-local time, converted via
  `Date`); the gate list shows the viewer's own local rendering
  (`toLocaleString()`) next to the event's declared-timezone rendering,
  plus the warning when present; a new "Timezone timeline" section reads
  the new endpoint.

## Limitations
- DST detection is offset-comparison based: correct for real transitions,
  but a window that happens to span two *different* transitions with the
  same net offset (vanishingly rare, no real zone does this on a normal
  schedule) wouldn't be flagged. Not worth the added complexity for a
  case with no known real-world occurrence.
- No safeguard yet for "does this event's declared `timezone` even make
  sense for a wall-clock time the organizer typed" beyond the DST
  crossing check itself (e.g. no validation against typos like a
  non-existent zone -- `EventSerializer.validate_timezone` already
  rejects those at the model level).
